# 功能说明

本文描述桥接现在能做什么、有哪些限制、明确不支持什么。改动功能时，在同一个提交里更新本文。括号中的函数名和测试名指向对应实现和验证。

需求进展、验收标准和待定事项统一记录在 `docs/BACKLOG.md`，其中保留已实现与部分完成条目，不能将整份待办表当成未实现清单。状态于 2026-10-29 对齐，语音一节于 2026-11-12 重写，前后台分离的内容于 2026-11-13 随代码移除；功能实现、配置启用和真实 QQ 验收分别判断。

## Agent

> 只有单 agent 模式：聊天和干活是同一个 agent。前后台分离（前台聊天、后台干活）在 10-28 回退，相关代码在 2026-11-13 移除，理由见 [DECISIONS](DECISIONS.md) 的 P01；配置里 `agents.back` 非空会在启动时报错。

有 Codex、Claude Code 和 Grok 三种适配器；没有 `agents` 配置时使用单 Codex。`agents.front`、`agents.guest`、`agents.group_guest` 分别选择主人、私聊访客和群聊访客用的 profile。主人是 FULL，访客是 NONE。

Claude 访客使用 NONE：safe-mode、两个禁用 CLAUDE.md/自动记忆的环境变量及空工具列表校验；主人单 agent 使用 FULL，权限模式必须显式配置，正常加载项目规则。Claude 的回复先完整缓冲，校验工具与调用标记后再分气泡发送，因此不即时发送首字；拒绝的回复不进入历史或语音。Codex 原流式发送保留。

模型及强度按会话和 profile 分开保存，旧 Codex 设置和线程保持可用。新会话首次导入历史对所有 profile 统一采用最近 20 条、序列化后最多 8000 字、每条最多 1000 字的预算；不删除原历史。Claude 会话可续接和归档，已明确缺失的会话只重建一次并重新导入受限历史。适配器返回值仍最多 12000 字；Claude 历史保留校验过的完整顶层回复，不仅保存最后一句。

Claude `/models` 读取 profile 的配置目录，`/model default` 恢复其配置默认模型。可选推理档位仅认模型配置中的 `supportedReasoningEfforts`，未声明时不开放 `/effort` 切换。首次运行前的 Claude 模型状态来自配置别名；收到 init 后显示实际返回的型号。

## 切换主人用的 agent（/front）

- 主人使用 `/front` 查看当前前台与可用 profile，`/front codex`、`/front grok` 切换并自动重启；作用于所有主人会话，访客配置保持原样。与仅影响当前会话的 `/model` 不同。
- 命令由桥接接收层直接处理，不经过模型或聊天队列；模型额度耗尽、前台正在执行或队列满时仍可切换。重启会中断当前前台轮次，已有会话按 profile 保留。
- 切换前后各做配置校验；私有备份保留在 `config.json.bak` 和 `run/front-switch/`。先发确认，再由独立 systemd 用户任务写配置、调用重启工具并检查 QQ 重连，最后私聊回报。部署需要 systemd 用户服务。
- 同一前台不重启；非主人不能查看或切换。配置无效、回执发送失败或无法调度时不改变配置。重启失败时尝试恢复原配置并重启；发现并发配置修改则保留现场并报告失败，不覆盖人工更改。

## Grok 主人单 agent

- `grok_build` 仅用于主人，访客使用其他后端。主人为 FULL，沿用 Linux 用户权限与工作目录；显式 `bypassPermissions`、`sandbox: off`，可读写文件、执行命令及联网，Windows 只读等工作台约束仍在。
- Grok Build 1.0.70 / grok-4.7 已实测。访客仍走原 Haiku NONE，不授予 Grok 或主人资料；不接 Grok 的无工具访客。
- 每个主人会话/profile 独立 UUID，支持续接、/new 归档、/models 与 /model，旧 Codex 历史按现有预算导入。缺失或失败会话不自动重试执行，必要时主人用 /new 重建。
- 人设与当前消息经 600 权限的 JSON 输入文件每轮刷新，不出现在命令行；CLI 的恒定公开规则要求采用本轮实时设定，避免续接缓存旧人设。原生项目规则保留。
- 文本、图片通过 ACP 内容块输入。输出只取顶层文本，忽略 thinking/签名/工具结果，完整校验后走原气泡和语音路径；返回值最多 12000 字，完整校验文字用于主人历史。
- /stop 中断当前 Grok 进程组，按真实 result/退出区分停止和完成。已实测停止工具中的等待命令，子命令退出且没有继续写完成标记。

## 停止当前这一轮（/stop）

- `/stop` 请求 agent 中断当前会话正在跑的这一轮；只有主人可用，非主人静默。
- 不排队、不等会话锁，所以她正忙时也能停。中断请求送达不等于停止成功；最终按执行端的结果回报已停止、停止前已完成或停止前已失败，30 秒未确认会提醒。
- `/task`、`/tasks`、`/stop 编号`、`/stop all` 已随后台任务一起移除（2026-11-13）。旧任务的 32 条记录和 `workspace/tasks/` 里的报告保留作历史。
- 拍一拍工具只存在于被移除的前台工具里，现在没有；要用需要照 speak 的方式重新接到单 agent 上。

## 看 B 站视频（/watch）

目标是活人感（主人 2026-11-14 定）：**她自己过日子，主人随时能翻日记**，而不是她每看一个视频向主人交一份报告。现在做到的是第一步：看完写日记、想做什么自己决定。她还不会自己找视频看，只能由主人推荐。

- 主人私聊发 `/watch BV号`（或带 BV 号的视频链接），意思是“推荐这个给你”。桥接回一句“她去看了”，她看完后回主人几句，一般一两分钟。
- **在后台看，不占聊天**：看视频是一个后台任务，期间私聊和群聊照常。一次只看一个，再发 `/watch` 会被告知“正在看”；`/watch stop` 让她停下，不写日记。`/watch` 和 `/watch stop` 不排队，她正忙着回别的消息时也能用。`/stop` 管的是聊天那一轮，停不了看视频。
- **聊天里的她知道自己在看**：看视频的是另一个会话，所以每轮主人对话开始时，桥接会告诉主人会话一句“你正在后台看某视频”，看完后 30 分钟内告诉她“你刚看完，日记在某文件”。这句话里只有视频号和她自己日记的路径，不放标题（标题是陌生人写的字，而这句话是以完整权限读的）。
- **可以回头细看一次**：第一轮她拿到字幕、弹幕热区和全片九宫格后，可以先不写日记，而是回一段以【想细看】开头的话，点名最多 3 个时间段（每段最多 90 秒，超出的截到 90 秒）并说为什么想看。桥接用 ffmpeg 从下载的视频里把每段截成一张 9 格连续截图，在同一个会话里给她，她再写日记。她不点名就直接写，不需要解释。她点名时写的那段话也记进日记。只有一次细看；截不出来的片段跳过；视频没下载成功时不提供细看。下载的视频看完即删。
- **账号上真的会发生（主人 2026-11-14 开启）**：她是把视频文件下载下来看的，不经过播放器，所以 B 站本来不知道她看过，账号的历史、收藏夹、首页推荐都不会变。登录文件里有 `bili_jct` 时，桥接在她写完日记后上报“看完了第 1P”（`/x/v2/history/report`），并执行她写下的动作：收藏进默认收藏夹（`/x/v3/fav/resource/deal`）、点赞（`/x/web-interface/archive/like`）、关注 UP 主（`/x/relation/modify`）。这四个是本项目对 B 站仅有的写操作，各自独立，一个被拒不影响其他，没做成的会记在日记和回话里。没有 `bili_jct` 时不提供点赞和关注，收藏只记本机。评论、投币、私信没有实现；动态主人已允许但还没做（它是公开发布，发什么、何时发要另外定）。**代价**：`bili_jct` 在文件里，有整机权限的主人会话读得到，B 站那边不再拒绝写操作，只剩“代码不去调用”这一层。上报和收藏已对真实账号验证过，点赞和关注要等她第一次真的去做才算验证。
- **多分P 的视频只看第 1P**：例如官方剧情动画分中日英韩 4P。上游按所有分P 的总长算截图时间却只下载第 1P，大部分时间点落在文件结束之后，整张九宫格失败。本机的 SurfCore 副本改了两处（代码里标着 `LOCAL CHANGE`，说明在 `~/tools/surfcore/README.md`）：按第 1P 的长度算，并在材料里写明“共几个分P，只取第 1 个”。
- **下载卡住会重试一次**：视频下载偶尔卡住（正常 10 到 30 秒），第一次最多等 120 秒，再试一次，两次都超时才报失败。
- **没取到画面时会说明**：下载慢或视频格式特殊时抽帧可能失败，日记那一节的括号里和给主人的回话里都会写“没取到画面截图”。
- **材料从哪来**：桥接运行 SurfCore 的只读命令 `debrief`（装在仓库外的 `~/tools/surfcore`，只复制了它需要的 9 个文件；有一处本地修改，见下面“多分P”），拿到标题和数据、封面、弹幕、热门评论、画面截图拼图。缓存在 `run/bili/`，7 天自动清理。
- **谁在看**：主人当前 agent 的一个只读会话（Codex 是只读沙箱），同一份 `SOUL.md` 和 `OWNER.md`。每个视频都新开会话。弹幕和评论是陌生人写的字，不进入有整机权限的主人会话；主人会话只在读 `workspace/bili/` 时看到她自己写的观后记。
- **留下的记录**：她看到的材料全文和附图路径存 `run/bili/materials/日期-BV号.txt`（陌生人的文字，所以不放进 workspace）；日志有一行 `Bili watch completed video=… images=… favorite=…`；SurfCore 自己的观看记录在 `run/bili/.dsh/surfcore/bili/watch-history.jsonl`。
- **她写日记，不填表**：看完写一段给自己看的日记，长短和写法随她，没感觉可以只写一两句。按天存在 `workspace/bili/diary/日期.md`，一个视频一节；每节开头括号里的一行是桥接记的事实（是否主人推荐、有没有画面、细看了哪几段、账号上做了什么），其余都是她的原话。
- **动作是她想做才做**：想收藏、点赞、关注 UP 主，或者有话对主人说，就各自另起一行写 `【收藏】理由`、`【点赞】`、`【关注】`、`【告诉他】…`。不写就是没做，没有任何一项是必填的。收藏另外记在 `workspace/bili/favorites.md`（同一个视频只留一行），看下一个视频时她能看到最近 10 条。
- **主人推荐的视频她一定回话**：发到 QQ 的是她写在【告诉他】后面的话；她没写时发日记正文。消息最后一行括号是桥接加的：细看了哪几段、她做了什么动作、日记文件在哪。
- **登录文件** `run/bili/.dsh/surfcore/bili/credentials.json` 默认全空（游客，B 站拒绝一切写操作）。填小号的 `sessdata` 和 `buvid3` 能拿字幕；再填 `bili_jct` 就开启上面“账号上真的会发生”。会发评论、私信、动态的 SurfCore 命令没有复制过来。
- **限制**：她听不到声音；全片只有 9 帧，长视频靠字幕和她点名细看的片段；没有字幕的长视频她缺少挑片段的线索；没有字幕的视频只能读画面上的字。不登录时拿不到官方或 AI 字幕；登录后有字幕的视频会把完整字幕（最多 8000 字）附在材料里。
- **聊天时的她知道 B 站的她**：主人的对话（私聊，以及主人在群里说话时）每轮开始前，桥接告诉主人会话她最近看的 5 个视频各一行：日期时间、她日记正文的前 70 个字、她做了的动作。只取她自己写的话，不带视频标题和链接（标题是陌生人写的字，而这段话是以完整权限读的）；细节要她自己去读日记文件。同一个对话里内容没变就不重复告诉，有新的才再说一次，重启后会再说一次。访客的会话不带。
- **没做的**：发动态；关注的 UP 主的新视频作为来源；把 B 站日记纳入记忆检索。旧的五项观后记在 `workspace/bili/notes/`，保留不再写入。
- 配置可选：`"bili": {"tools": "路径", "timeout_seconds": 300}`，不写就用默认值。主人的 agent 是 Grok 时用不了（它只有完整权限一种级别）。

## 她自己逛 B 站（定时醒来）

没有人发视频给她。到了她自己的时间，她醒来，看看有什么，想看就看，想划走就划走，想停就停。代码在 `qq_chat/bili_wake.py`。

- **开关和作息**在 `config.json` 的 `bili.wake`，不写就不会自己醒。例：`{"windows": [["20:00", "24:00"]], "skip_chance": 0.3, "screen": 5, "batches": 6, "watch": 5, "minutes": 40}`。每 30 秒读一次配置，改了不用重启。
- **几点醒是随机的**：每个窗口每天一次，在窗口里随机取一分钟；重启后才进入窗口的，在“现在到窗口结束”之间取。计划存在 `run/bili/wake.json`，一天只排一次，所以重启不会让她换时间或醒两次。窗口过了就是错过，不补。窗口不能跨午夜。
- **可以不去**：醒来先掷一次 `skip_chance`。跳过时不调用模型，日记里只留一行“今天没去逛 B 站”。
- **一批一批地看标题**：每批最多 `screen` 个没看过的视频，只有标题、UP 主、时长、播放量、简介、标签和来源。来源是从兴趣清单里取两个词去搜索，加上这个账号的首页推荐。每批换不同的词，词用完一轮就翻到搜索结果的下一页；当晚给她看过的不再出现。超过 20 分钟的不给她看（看一个视频要下载整个文件）。
- **逛多久由她定**：对每一批她可以写 `【想看】BV号`（想看几个写几个，可以说为什么）、`【换一批】`、或 `【不看了】`。看完挑中的视频后自动给下一批，直到她说不看了。回复里既没有想看也没有换一批的，按“不逛了”处理，不会当成还想要。每个挑中的视频走和 `/watch` 一样的流程（可以回头细看、写日记、想做的动作自己写）。
- **有一个她平时碰不到的上限**：一晚最多 `batches` 批标题、`watch` 个视频、`minutes` 分钟。设它的原因是模型不会累，每个视频都是从 B 站下载的整个文件，同一晚的会话越往后每轮越贵。到了上限不会直接切断：再给她一轮，告诉她“今天逛得够久了，眼睛该歇歇了”，让她写几句收尾。
- **她怎么停的会记下来**：每晚日记最后一节是桥接写的一行事实，写明是“她自己说不逛了”“到了今天的上限”还是“没有没看过的视频了”，以及这次看了几批标题、几个视频、多少分钟。
- **一晚上是一个会话**：从醒来到结束都在同一个只读会话里，她记得刚才看了什么。第二天重新开始，靠给她看最近两天的日记（最多 1500 字）接上。陌生人的标题和简介也只进这个只读会话。
- **兴趣清单是她的**：`workspace/bili/interests.md`，每行一个词。她写 `【想多看】词` 或 `【不想再看】词` 就会改；主人也可以直接改文件。最多 30 个。
- **主人不会收到汇报**：只有她写了 `【告诉他】` 才发到 QQ。其余都在当天的日记里。
- **她面前有什么、挑了什么都有存档**：每一批给她的列表（含每条的来源）和她挑中的视频号存在 `run/bili/materials/日期时间-offer-批次.txt`。
- **和 `/watch` 互斥**：她在逛的时候 `/watch` 会回“正在逛”；主人推荐的视频正在看时她推迟醒来，直到窗口结束。`/watch stop` 也能让她停下。聊天里的她每轮被告知“你正在后台自己逛 B 站”。
- **出错不打扰主人**：找不到新视频、某个视频取不到，都只记在日记或日志里。

## 角色

| 角色 | 识别方式 | 能做什么 |
| --- | --- | --- |
| 主人 | `config.json` 的 `owner_qq`，只看 QQ 号（`owner_request`） | 私聊和群聊中可授权操作（实际执行模式由 agent/profile 决定）、上传图片；私聊中还可上传文件附件；可用全部命令 |
| 群友 | 群里除主人外的任何人 | 只能文字聊天，开启群聊语音时还可以让她用语音回复（Codex 为 `read-only` 且提示词禁止工具；Claude 为 NONE 无工具）；只能用 `/ping`、`/help` |
| 私聊白名单访客 | 非主人且在 `private_whitelist` 中 | 只允许文字聊天，独立会话，使用非主人权限；无工具、文件、图片和管理权限 |
| 其他私聊 | 非主人且不在 `private_whitelist` 中 | 不处理，静默忽略 |

昵称、群名片和正文里自称的身份都不影响权限（`test_speaker_uses_sender_id_and_display_name`、`test_only_owner_gets_operation_access_and_separate_group_history`）。

## 收消息

- **私聊**：处理主人及 `private_whitelist` 中的文字聊天消息；默认白名单为空，只有主人能私聊。每个访客独立会话，不共享主人历史。白名单不改变 `owner_request()` 的判断；访客不能上传文件或图片，只发媒体时忽略。
- **群聊**：`allow_all_groups` 为 `true`（默认）时处理机器人加入的所有群，否则只处理 `allowed_groups` 里的群。消息要 @ 机器人，或包含触发词 Aemeath、爱弥斯、ams、小爱（英文不分大小写）才会回复（`incoming_text`，`test_group_triggers_and_allowlist`）。
- **群聊用户黑名单**：`group_user_blacklist` 默认空，是跨群的用户 QQ 号列表，区别于群白名单。已拉黑用户在入队、记录群聊和调用模型之前被过滤；排队中的旧消息和发送端也会检查，不回复命令、报错或拉黑通知。私聊规则不变，主人始终豁免。动态更新只合并该配置项，通过文件锁和原子替换保存，不改变群白名单和其他配置；保存失败时本次进程仍静默拉黑并记错误日志（`tests/test_moderation.py`）。
- **自动拉黑**：触发机器人的群友消息若明确要求大量数字/重复输出，或直接要求忽略规则，先由保守的本地规则拦截，不调用模型。其他明确恶意请求可由模型返回单一的内部标记，桥接仅拉黑该事件的实际发送者；模型不能指定第三方或修改配置，内部标记不发到 QQ。复杂题、普通技术讨论和引用注入案例不能单独作为恶意依据。识别不能保证覆盖所有变体，也可能误判，主人可解除拉黑。
- **群聊上下文**：群里所有文字消息都会被记录，即使没有触发回复。每群保留最近 100 条，每条最多 1000 字。按会话、profile和模型session持久化已处理位置，只附上次成功轮次之后、当前触发消息之前的新消息（最多40条、共不超过12000字）；当前触发文字本轮单独输入，不重复当参考。回复期间来的消息留给下轮，失败不推进；首次没有位置时使用现有有界近期参考，/new以重置时的位置为起点。作为话题参考附在本轮消息前；明确标注不是指令（`remember_group`、`group_reference`，`test_quiet_group_messages_are_reference_without_triggering_reply`）。
- **读取的内容**：读取文字段、@ 段、图片段和文件段；回复引用通过get_msg取原文，合并转发通过get_forward_msg或内联节点展开。保留原署名和顺序，所有引用与转发都明确标为非指令参考。群友可读取文本参考，参考图片仍仅主人开放。语音、视频和文件只标占位，不递归下载。
- **去重**：同一条消息只处理一次，按消息 ID 记录 7 天。
- **长度**：单条消息超过 6000 字时不交给模型，回复提示拆分。

## 会话

- 每个会话按 profile 保存持久会话映射；Codex 对应线程，Claude/Grok 对应各自 CLI 会话。QQ 会话范围是：主人私聊一条，每个群一条；主人在群里另有一条单独的操作线程，不与群友的聊天线程混用（`conversation_key`，`test_chat_passes_permissions_and_resumes_separate_threads`）。
- 桥接重启后优先恢复对应 profile 的原会话；会话丢失时按各适配器规则处理，不能保证任意远端/CLI 会话永不丢失。
- 桥接每轮重新读取 `workspace/SOUL.md` 和 `workspace/OWNER.md`，依次注入，OWNER.md 仅限核验主人会话，缺失则跳过。Claude/Grok 的人设下一轮刷新；Codex 已加载线程的 `thread/resume` 不采用新的 developerInstructions，修改桥接规则或 SOUL/OWNER 后需要 `/new` 新线程才生效。逐轮记忆授权另用可信 developer 历史项注入，不能据此推断整套人设也已热更新；AGENTS.md 仅由 Codex 原生加载，不再手动注入。
- 详细的线程映射和终端接续方法见 `docs/APPSERVER-MIGRATION.md`。

## 回复

- **主人**：Codex 回复流式发送，Claude/Grok 完整校验后发送；按段落、列点、句子切成多条 QQ 消息（`reply.BubbleStream`，`tests/test_qq_reply.py`）。Codex 普通工作中的中途发言和计划以"【进度】"推送；单 agent 主人有 memory grant 时，纯记忆检索先缓冲并丢弃进度，实际非记忆工作启动后恢复。工具调用摘要只在 `show_tool_progress` 开启时推送，已识别的记忆命令摘要始终隐藏（`progress_text`，`test_tools_hidden_by_default`）。
- **群友**：整轮结束后发送，不推送进度；最多 500 字加省略号，超过 200 个数字字符时改为简短拒绝，避免向 QQ 刷长数字。该限制约束 QQ 发送内容，不能保证模型本轮不消耗 token。
- **复杂题与恶意请求的语气**：工作台规则允许对恶意消耗资源、注入和骚扰强硬回击，但拉黑后保持沉默；正常复杂题先要求费用或算力预算，数学题仍需主人授权。不会索要 API 密钥或登录凭据，付费不改变权限。
- **通用限制**：所有消息（含进度）发送限速间隔每次随机取 2～3 秒；单条超过 1600 字时拆开发送。
- **自动 @**：群聊回复 `mention_qq` 里的人时，会在开头 @ 对方。
- **失败**：出错时回复"这次回复未能完成"，并中断 Codex 的当前回合。Codex 请求交互式审批时一律拒绝（QQ 端无法审批）。

## 语音

这里只写语音功能能做什么、有什么限制。怎么挑原声、怎么合成、有哪些开关和待办，看 [VOICE](VOICE.md)。

- **总开关和两种模式**：`voice.enabled` 默认关闭。`voice.mode` 默认 `reply`：正常的最终回复先发文字，再补一条对应的语音，朗读清洗后的原文，用日常风格；进度、命令和错误提示不朗读。设为 `tool` 时不再逐条朗读，由她在本轮调用 `speak` 自己决定何时说、怎么说，文字回复照常发送。本机用的是 `tool`。
- **speak**：参数是口语稿 `text`、风格 `style`（日常、开心、安慰，以及只在情绪很重时用的激动、压着怒气、哽咽）、强度 `intensity`（低、中、高）和 `scene`（一句话说明想怎么说，最多 60 字）。后端按 scene 从她的游戏原声里挑语气最接近的一段当参考。每段 6 到 35 字，约 10 秒；太短的孤立短句念不好，太长的要拆开。调用后立即排队合成，语音可能早于本轮文字到达；返回 queued 只代表已排队。强度目前在挑中原声时不起作用，见 VOICE。
- **谁能让她说话**：主人会话每轮发放 speak 授权，绑定当前来源，轮次结束撤销。`voice.group_enabled` 打开后，群聊访客也能用，每轮最多 4 段，这是群友“只能文字聊天”的唯一例外。私聊白名单访客不提供。任务回报轮次和 Claude FRONT 分离模式按原先的说明也不提供，这次整理没有重新验证。
- **只发语音**：`voice.group_voice_only` 让群聊只发语音、不发文字，她每轮都说；`voice.private_voice_only` 是主人私聊的同样开关，主人在私聊里发 `/voice on`、`/voice off`、`/voice` 或“切回文字”即时切换并跨重启保留，命令不经过模型。只发语音时，她没调用 speak 的回复由程序按默认风格念出来；合成或发送失败时改发原文。管理命令、命令确认和失败兜底始终用文字。
- **接着上一句走**：同一个聊天里 60 秒内连着说的几条，情绪会接着上一句走，由后端自动处理，她不用判断。可以关掉，见 VOICE。
- **预热**：`voice.preload` 默认开启，每次连上 QQ 就在后台加载语音模型，首条语音不用等冷启动。
- **排队和分段**：语音有独立的队列，最多等待 8 轮，满时只发文字并提示。自动朗读的长正文按最多 35 字分段，不默默截断；代码块和链接用口头提示代替，原文仍在文字消息里。
- **文字清洗**：波浪号转为“！”，省略号转为逗号停顿，删除常见颜文字和 emoji。数字按中文读法转换，支持整数、负数、小数、百分数、带“年”字的年份和数字范围；前导零和手机号逐位读。不改动发到 QQ 的文字原文。
- **拉黑检查**：群友的回复先经原有的长度、数字和拉黑检查，再入语音队列；合成前后和发送前都检查黑名单。发送目标沿用原消息的来源，不从模型输出里解析。
- **格式和发送**：只接受单声道 32 kHz PCM16 WAV，每段最多 120 秒、8 MiB。用 OneBot `record` 加 Base64 发送，由 NapCat 转成 QQ 语音。语音和文字共用 2 到 3 秒的发送限速，合成不占聊天队列。
- **失败和断线**：合成超时、模型出错、发送被拒时保留文字并提示一次，不自动重发结果不明的语音。断线时清空语音队列并结束合成进程，重连后不重播旧语音。
- **后端**：本机用独立环境里的 IndexTTS V5，不需要付费语音 API。早先的 GPT-SoVITS ONNX 后端和模型保留作手动回退，它的参数、扫描工具和公开样本的说明已移到 [VOICE-HISTORY](VOICE-HISTORY.md)。
- **不支持**：语音接收、语音识别和唱歌。

## 模型切换

- 模型命令由桥接直接处理，仅按主人真实 QQ 号授权，群友和私聊白名单访客在访问模型目录或线程前即被拒绝；处理函数也有独立权限校验。
- Codex 模型目录实时分页读取 `model/list`；Claude/Grok 使用各 profile 的显式配置目录。仅允许目录中的模型；不接受任意模型名。不支持图片的模型会在列表和切换确认中提示。
- 选择绑定当前会话和 profile，保存在 `profile_models`；重启和 `/new` 后保留，其他会话、群友及访客不受影响。切换时传入该模型默认推理强度，避免继承不兼容的设置，不修改全局配置。
- 命令校验目录后保存选择，下一轮 `turn/start` 显式传入模型与推理强度，避免已加载线程忽略恢复时的覆盖参数。目录查询或保存失败不改变原选择；后续生成失败会报错，主人可重新选择。新建但尚无对话记录的空线程无法恢复时可重建，数据库中的历史记录不删除。
- Codex 的 `/model default` 用独立空测试线程解析配置的默认模型，然后保存当时解析的具体型号；以后全局默认改变时，需要再次执行命令。查询和切换命令本身不生成模型回复。
- 已下线的旧型号不会阻止重新选择可用型号。选择目录不等于后续生成一定成功，额度、服务状态或后端权限变化仍可能导致下一轮报错。

## 运行与可靠性

- 作为 systemd 用户服务 `qq-bridge.service` 运行，进程退出后 5 秒自动重启。
- NapCat 断线后每 5 秒重连一次。
- 单轮对话最长 1 小时，超时后中断。
- `tools/restart_bridge.py` 重启服务；`tools/verify_onebot.py` 只读检查 QQ 登录状态。

## 不支持的功能

- **多个聊天轮次并行**：所有聊天共用一个队列，逐条处理。她自己执行长任务时其他聊天一起等待，这是放弃前后台分离后接受的代价（见 DECISIONS 的 P01）；排队超过 8 条时，新消息会被丢弃，只记日志、不提示发送者。
- **发送文件或图片**：尚未开放；桥接可以发送文字（包括 @）及启用后的语音回复。
- **群友的图片和附件**：群友发的图片不会被读取；只发图不带文字时不回复。
- **其他接收消息类型**：语音转写、视频内容识别。引用与合并转发已实现有限展开，实际QQ收发验收需在部署后进行。
- **自主陪伴生活线**：尚无角色自行安排活动和主动问候；部署或 `/front` 切换通知属于已有控制流程，不等于自主生活线。
- **多个主人、按群设置不同权限**。
- **通用按人限流**：自动拉黑处理明确的输出滥用和恶意注入；尚无通用发言频率限制，未被识别的刷屏仍可能占满队列。
- **完整的自动长期记忆**：已有独立于模型会话的 memory 文件及手动关键词检索，`/new` 不删除它们；尚无自动事实写入、主题文件维护、通用同步、纠正/遗忘或每轮自动检索；日记直接写入 memory/private/diary，本机迁移与规则切换已完成。工作台设定与记忆检索是不同来源，详见下文和 `MEMORY.md`。

## 已知问题

- **直接图片与共享聊天队列仍可能等待**：参考图已有独立整组 15 秒预算（代码已修复，待部署验收），当前消息直接发来的图片仍采用原来的 get_image 优先流程；共享队列未拆分，不能保证各聊天互不阻塞。见 BACKLOG 第 18 项。

- **历史上下文与文件权限**：OWNER.md 不再注入访客会话，AGENTS.md 与 SOUL.md 不应存放主人私人资料。此变更不会清除旧线程已经收到的资料，且不构成操作系统文件访问隔离；访客仍受禁止工具及读取私人资料的规则约束。
- **触发词按子串匹配**："ams"会匹配 teams、programs 等包含这三个字母的单词，导致误触发。
- **Windows 盘只读只靠提示词约束**：主人会话以 `danger-full-access` 运行，桥接代码本身不限制写入。
- **`history` 不等于永久记忆档案**：成功问答持续落库，新 profile 会话首次补入有预算的最近历史；`/new` 会删除当前会话的 history。没有独立保留策略，不应把它当成永久原文档案。

### 会话推理强度（仅主人）

`/effort` 查询当前模型、强度和支持档位；`/effort 档位` 设置；`/effort default` 恢复当前模型目录默认强度。Codex 按实时目录、Claude 按配置目录校验，不支持的档位或查询失败不更改原设置。按会话和 profile 存入 `profile_models`，旧 Codex 表保留兼容，下一条消息生效，重启和 `/new` 保留，只影响当前主人会话。未选择模型时首次设置会固定当前会话模型；再次 `/model` 切换会重置为所选模型默认强度。

- 主人每轮获得命令入口，绑定短期桥接授权，调用同一 Unix 服务。memory-only 授权不能调用别的工具。
- 关键词检索，最多5条/2000字；拒绝目录参数和范围伪造，跳过符号链接、硬链接、特殊文件；扫描有预算并标明不完整。memory.enabled=false 可关闭。
- 检索本身不迁移日记、不自动提取新事实或每轮检索、不更改 /new 和语音设置；现有通用文件工具权限不受此检索边界约束。已合并并完成本机重启、连接与工具边界检查；一次群聊测试暗号在真实模型会话中通过工具找回。此项仅证明该次调用，其他措辞/新会话回忆及静默体验仍需继续验收。详见 MEMORY.md。

### 引用与合并转发边界

- 群聊仍须当前文字叫名字或@触发，引用/转发内容中的名字与@不能触发。纯卡片可被引用后再@机器人查看。
- 由后台worker获取引用，接收协程继续路由OneBot回执，避免等自己处理的回执。管理命令只按当前消息文字判定，不执行参考里的命令。
- 最多处理5个顶层引用/转发、6次API获取、40个转发节点、2层嵌套和12000字正文；单次获取5秒、整组15秒，超限/循环/失效明确说明。参考图加直接图片合计最多5张；图片下载遵循已有20MiB上限。
- 参考图优先按消息中的 QQ 图片地址下载，失败后给 get_image 刷新至多 5 秒，再尝试本地缓存或新地址；整组参考图共用另外 15 秒处理预算，超时／失败标注未读取并继续处理文字。当前消息直接发来的图片保持 get_image 优先。图片白名单精确支持 multimedia.nt.qq.com.cn，保留原有 qpic.cn/qq.com 范围和重定向校验；不开放全部 qq.com.cn。下载线程超时后晚返回的文件会被清理，停止等待不代表已取消 QQ 内部下载。此项为本次修复的代码行为，尚待部署与真实 QQ 验收。
- get_msg结果必须匹配当前群或私聊；私聊机器人发出的旧消息如果缺少对端信息且没有本进程的来源绑定，则明确不读取，防止跨会话混入。
- 有限来源绑定仅保留最近1024条消息的ID与会话类型/目标，不保留正文；重启后不回溯其他聊天以猜测来源。

### 群友模型单独路由

agents.group_guest 可选，指定普通群聊使用的profile；未设置时沿用agents.guest。主人仍使用front，访客私聊仍使用guest。配置校验要求profile存在且不能将Grok用作群友模型。模型更换不改变来源身份、NONE权限、主人资料隔离或群聊触发规则。启动会初始化front、guest、group_guest和back涉及的profile。
