## P01 · 2026-10-28 · 放弃前后台分离，回到单 agent

**补记说明**：这个决定当时没有写进任何文档，只留下一个配置备份的文件名和任务表里的记录。2026-11-12 助手评审项目时发现约三分之一的代码在为没启用的模式服务，主人才讲了原因，按主人的说法和仓库里的痕迹补记在这里。

### 原来想做什么

主人最初的设想：前台模型只负责聊天，遇到要动手的事就派给后台 agent 去做，后台做完把结果交回前台汇报。这样后台干活的时候，前台还能继续聊天或处理别的事。要解决的问题是：一件长任务跑起来，聊天就得跟着等。

设计见 [FRONT-BACK](FRONT-BACK.md)，分成 PR1 到 PR5 五步。

### 实际做了什么

| 时间 | 事情 |
|---|---|
| 10-27 16:50 | 设计文档写出，当天改到第四版 |
| 10-27 17:23–21:08 | PR1（抽出 agent 接口）、PR2（Claude 适配器）、PR3（后台任务、停止、回报）、PR4（前台工具通道）依次合并 |
| 10-27 19:50 | 分离模式开始实际使用：前台 Claude Sonnet，后台 Codex |

| 10-28 下午 | 接入 Grok 单 agent、加上 `/front` 紧急切换命令、写出统一 agent 接口的设计稿（至今没有实现） |

分离模式一共用了不到 17 个小时，派了 32 个任务（29 个完成、2 个被停止、1 个被中断）。PR5（多个后台）没有开始。

### 为什么放弃

主人用下来发现两个问题：

1. **干活的不是说话的那个。** 前台没有亲自参与工作，问到细节时说不清楚。
2. **工作汇报和聊天混在一起。** 两种对话挤在同一个会话里，结果工作没做好，天也没聊好。

助手的看法：这两条都是设计本身带来的，不是哪里没做好。第一条缺的是经历而不是能力，所以当时在 LESSONS 里记下的方向“给前台更多工具”治不了它。同样的设计不该再原样回来。

### 决定

主人决定回到单 agent：主人会话里的模型自己聊天、自己动手。

### 接受的代价

- 她干长活的时候，聊天要等。原来想解决的问题没有解决。
- 聊天和工作都在同一个会话里，会话越来越长，每一步都越来越慢，现在靠 `/new` 手动重开。

以后如果有人只看到这两个代价，又想把前后台提出来，先读上面“为什么放弃”。要重新考虑，新方案至少得回答：说话的那个怎么拿到干活的细节，汇报走哪条通道才不和聊天混在一起。

### 留下了什么

- **还在用的**：agent 适配器这一层。私聊访客用 Claude，群聊访客用单独的只读 Codex，主人可以用 `/front` 在 Codex 和 Grok 之间切换。
- **留在代码里但没启用的**：后台任务、任务命令、前台工具通道和 FRONT 权限级别。配置里 `back` 为空时它们不起作用。相关的说明还留在 FEATURES、ARCHITECTURE、README 里，各处已标明本机未启用。
- **要不要删**：还没定。助手建议先做一次依赖分析，列出能安全删掉的部分，再由主人决定。
- **文档**：FRONT-BACK 保留作历史设计；BACKLOG、ROADMAP 里“等 PR5”“前后台改造完成前暂停其他功能”之类的说法已失效。
